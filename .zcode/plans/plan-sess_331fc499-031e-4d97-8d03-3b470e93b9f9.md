# 4CoreFinSupport — Comprehensive Professional Review & Implementation Plan

## VERDICT: NOT READY

The product has a solid conceptual foundation and several well-engineered subsystems (audit hash chain, PII encryption, CSRF defense, state machine). However, it has **critical database integrity violations, a performance architecture that will collapse under real load, a role-switching security vulnerability, and essentially no product documentation**. It requires significant corrections before enterprise production use.

---

## PART 1: EVIDENCE-BASED REVIEW (Summary of Findings)

### What is Good
- **Audit hash chain** (GAID-style SHA-256 chain) is well-implemented and enforced at DB level (trigger prevents UPDATE/DELETE)
- **PII encryption** at rest using AES-256-GCM with proper IV/tag separation
- **CSRF double-submit token** + same-origin check on all state-changing requests
- **Ticket state machine** with role-gated transitions and required-field enforcement
- **Tenant isolation** architecture with deterministic tenant IDs and RLS policies as defense-in-depth
- **Supabase Auth** as sole identity provider (production-safe, no local password auth)
- **SSE real-time broadcasts** properly scoped by tenant
- **Design system** is well-documented with tokens, typography, spacing, and accessibility guidelines
- **Idempotency middleware** for POST/PUT operations
- **Account lockout** with failed-login tracking
- **Forced password change** gate for admin-provisioned accounts

### What is Dangerous

**P0-1: Database CHECK constraints are stale and will reject valid data**
- `supabase/migrations/003_indexes_and_constraints.sql:39` — `chk_tickets_status` allows only `('RECEIPT','ASSIGNED','INVESTIGATE','RESOLVED','CLOSED')` but the app uses 3 more statuses: `WAITING_CUSTOMER`, `WAITING_PARTNER`, `WAITING_INTERNAL`
- `003:37` — `chk_users_role` allows only `('SUPER_ADMIN','BU_SUPPORT','PROVIDER','EXECUTIVE','PARTNER')` but the app uses `BU_SUPPORT_L1`, `BU_SUPPORT_L2`, `BU_SUPPORT_L3`, and `CUSTOMER`
- **Evidence**: `src/types/app.ts:7-9` (enum includes WAITING_*), `src/types/app.ts:20-28` (enum includes L1/L2/L3/CUSTOMER), `server/rbac.ts:74-104` (roles defined)
- **Impact**: Any attempt to INSERT a ticket with WAITING status or a user with L1/L2/L3/CUSTOMER role will fail at the database level

**P0-2: Role-switching UI allows privilege escalation**
- `src/App.tsx:232-254` — The user dropdown in the top bar lists ALL users and allows clicking to switch `currentRole` to any user's role. The `handleRoleChange` function changes the active role for the session.
- **Evidence**: `src/App.tsx:238` — `onClick={() => { handleRoleChange(u.role as UserRole); ... }}`
- **Impact**: Any authenticated user can switch to SUPER_ADMIN role client-side. While backend checks use the JWT role (which is correct), the frontend exposes all admin UI, tabs, and data to any user who switches roles.

**P0-3: GoLive document contains plaintext admin credentials**
- `docs/25_GoLive_QA_and_Auth_Migration.md:48-53` — Contains email `peteslimmy@gmail.com` and plaintext password `@Pete12345678`
- **Impact**: Credential exposure in version-controlled documentation

**P0-4: `.env` file visible in git status**
- Git status shows `M .env` — environment file with secrets (SUPABASE_SERVICE_KEY, JWT_SECRET, ENCRYPTION_KEY) is being tracked
- **Impact**: Secrets in version control

### What is Wrong

**P1-1: RLS policies are bypassed by the service_role connection**
- `server/supabase.ts` connects with `SUPABASE_SERVICE_KEY` which has `BYPASSRLS`. All queries bypass RLS. Tenant isolation relies solely on application-level `.eq('tenant_id', ...)` filters.
- `supabase/migrations/010_rls_backstop.sql:5-6` explicitly documents this: "The Node server connects with the service role (BYPASSRLS), so this file does NOT gate the application."
- **Impact**: Any bug in application-level tenant scoping (e.g., a missing `.eq('tenant_id', ...)`) leaks cross-tenant data. Defense-in-depth is incomplete.

**P1-2: N+1 query pattern — listCustomers loads ALL tickets to compute counts**
- `server/repository.ts:613-641` — `listCustomers()` queries all tickets for the tenant, then iterates in JS to build a count map. With 10K tickets, this fetches 10K rows per customer list request.
- **Evidence**: Lines 613-623: `const { data: tickets } = await ticketQuery;`
- **Impact**: O(N×M) where N=tickets, M=customers. Will timeout under production load.

**P1-3: SLA job uses volatile in-memory notification deduplication**
- `server/slaJob.ts:11` — `notifiedMap` is a plain `Map` that resets on every server restart. After restart, all notifications re-fire.
- **Impact**: Notification spam after deployments; no true deduplication.

**P1-4: SLA business-hours calculation has timezone bugs**
- `src/lib/slaCalculator.ts:130-131` — Uses `cur.getHours()` and `cur.getMinutes()` which return local browser/server time, NOT the tenant's configured IANA timezone. The `tzName` parameter is accepted but never used for time conversion.
- **Evidence**: Lines 130-131 use `cur.getHours()` directly; `tzName` is accepted at line 100 but only referenced in a comment.
- **Impact**: SLA deadlines are incorrect for any tenant not in the server's local timezone.

**P1-5: No WAITING_* state transitions in the state machine**
- `src/lib/ticketStateMachine.ts:72-192` — TRANSITIONS array has no rules for entering WAITING_CUSTOMER, WAITING_PARTNER, or WAITING_INTERNAL states.
- `src/types/app.ts:7-9` — These statuses exist in the enum.
- **Impact**: Tickets cannot legally enter waiting states via the state machine, yet the SLA job (`server/slaJob.ts:27`) correctly excludes them from breach detection. Dead status path.

**P1-6: BU_SUPPORT_L1/L2/L3 have identical permissions — no differentiation**
- `server/rbac.ts:56-96` — All three tiers share `BU_SUPPORT_PERMISSIONS` array with zero differences.
- **Impact**: The tiered escalation model described in role descriptions ("First-line", "Senior", "Lead") is purely cosmetic. No actual permission differentiation exists.

**P1-7: Validation schemas use `.passthrough()` allowing arbitrary fields**
- `server/validation.ts:44,71,78,84,93,100,112,131,135` — Every Zod schema calls `.passthrough()`, allowing unknown fields through to the database.
- **Impact**: No input sanitization. Arbitrary keys can be stored in records.

**P1-8: `replaceJsonTable` is not atomic — DELETE ALL then INSERT**
- `server/repository.ts:801-815` — Deletes all rows, then inserts new ones. No transaction wrapper. If the insert fails, all data is lost.
- **Impact**: Data loss on partial failure. Race condition between concurrent admins replacing the same config.

**P1-9: `requireAuth` uses async callback anti-pattern**
- `server/auth.ts:417-442` — Uses `Promise.resolve().then()` instead of making the middleware `async`. If the inner promise rejects after `next()` is called, the error is unhandled.
- **Impact**: Potential for hanging requests or unhandled rejections.

**P1-10: Partner access control relies on string matching, not FK**
- `server/auth.ts:483-487` — `canAccessTicket` for PARTNER role compares `partner` string values with `ilike`. If partner names differ by case/spacing, access is denied.
- `server/repository.ts:94` — `query.ilike('partner', partnerNameFor(user))` — same pattern.
- **Impact**: Fragile. Partner "Adyen" vs "adyen" would cause access failures.

### What is Missing

**P2-1: Documentation is almost entirely stubs**
- 22 of 26 docs files are 1-7 lines. No real PRD, no FRD, no architecture doc, no API specification, no SLA specification, no workflow documentation, no security specification.
- **Evidence**: `docs/02_PRD.md` (7 lines), `docs/03_Functional_Requirements.md` (3 lines), `docs/05_System_Architecture.md` (2 lines), etc.

**P2-2: `usePermissions` and `useHasPermission` hooks are stubs**
- `src/hooks/queries.ts:513-522` — `usePermissions` returns `[]`, `useHasPermission` always returns `true`.
- **Impact**: Any code using these hooks for UI gating is broken.

**P2-3: No transition rules for WAITING states or REOPEN from CLOSED→INVESTIGATE**
- The CLOSED→INVESTIGATE REOPEN transition exists but has no `from: TicketStatus.WAITING_PARTNER` transition (partners cannot respond to waiting-for-partner tickets).

**P2-4: No database-level enforcement of ticket state transitions**
- State machine is app-level only. Direct DB writes can put tickets in any state combination.

**P2-5: No test coverage for authorization/permissions, partner isolation, or SLA calculations with timezones**

**P2-6: No configuration for WAITING status pausing SLA timer**
- The SLA job excludes CLOSED and RESOLVED from monitoring but doesn't handle pausing/resuming SLA for WAITING states.

## EXECUTION APPROACH

Each phase will be implemented fully before moving to the next:
1. **Write the code changes** for all items in the phase
2. **Run tests** (`npm test`) to verify nothing breaks
3. **Run lint** (`npm run lint`) to verify code quality
4. **Confirm all items** in the phase are complete
5. **Update relevant .md files** per Phase 3
6. **Move to next phase**

For Phase 3, all 12+ documentation files will be rewritten with substantive content derived from the actual codebase, not aspirational documents.

The total estimated scope is ~40 discrete changes across 4 phases.
